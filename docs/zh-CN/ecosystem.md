# 一个身份上下文，两种支持方式

[English](../ecosystem.md) | [简体中文](ecosystem.md) · [项目概览](../../README.zh-CN.md)

DevWho 的目标很简单：选择一次开发者上下文，让从该终端启动的工具使用它。上下文可以代表个人工作、客户项目，或共用电脑上的某位使用者。项目目录和已安装的工具都可以保持原样。

这个目标有两个互相独立的部分：

| 部分 | 工作方式 | 状态 |
|---|---|---|
| **原生环境约定** | 应用读取共用的 `DEVWHO_PROFILE`，并按自己的配置选择账号。任何启动器都可以提供该变量。 | 提案中；本仓库尚未提供原生应用集成。 |
| **兼容核心** | DevWho 将已保存的 profile 转换为现有应用已支持的接口，例如 Git 运行时配置和 `GH_CONFIG_DIR`。 | Python、Go、Rust、Bash 独立实现都遵循共用契约。 |

支持该约定的应用不必导入 Python 模块、安装 DevWho、读取 DevWho 的 TOML 文件，也不必调用守护进程。兼容核心的使用者最终只需为自己的机器选择**一种实现**，不需要安装四种语言环境。

## 先定义约定

代理环境变量是一个有用的参考：应用读取共用约定，并自行实现相应行为。约定与具体实现彼此独立。变量拼写和优先级仍然很重要，例如 curl 处理 HTTP 时刻意只接受小写的 `http_proxy`。[curl 的说明](https://everything.curl.dev/usingcurl/proxies/env.html)

DevWho 的初版草案只使用一个变量：

| 变量 | 含义 |
|---|---|
| `DEVWHO_PROFILE` | 当前所选的本地上下文，例如 `personal` 或 `work`。 |

应用会把该上下文映射到自己的现有账号。例如，`work` 在一个工具中可以选择公司的 Git 托管账号，在另一个工具中则选择公司组织。映射由应用管理；密码和令牌继续留在各自原有的凭据存储中。同一个 profile 标签不代表它在每个服务中使用相同用户名。

我们不引入 `DEVWHO_<APP>_USER` 这一类变量、通用令牌或共用凭据目录。Git author 姓名和邮箱并不是通用登录标识。只有具体使用方确有需要、且跨应用含义清楚时，才应增加字段。

[环境规范](../../spec/environment-v1.zh-CN.md)定义变量拼写、校验、继承、缺失值、优先级和账号选择失败时的行为。**该规范仍是草案。** 当前 v0.1 已会导出 profile 标记；未来的原生使用方可以直接读取它。真正的支持还需要应用自己的账号映射和正常认证流程，不能只在环境中放一个标记。

一个稳定的选择器不需要配套的版本变量。保持其含义稳定，单独评审扩展；只有解析器确有需要时，才保留配置文件版本。要提供 `DEVWHO_PROFILE=work`，既不需要 TOML，也不需要 Python：普通的 dotenv 启动器就能加载它。当前所有 core 都读取完整 TOML profile，并支持显式选择的[字面量 dotenv 输入](../../spec/dotenv-v1.zh-CN.md)；dotenv 只选择一个通用环境变量 profile，不与 TOML 合并。

## 现有工具目前如何工作

Git 和 GitHub CLI 通过各自已有的接口获得支持。本仓库并未声称它们会读取拟议中的 DevWho 约定。

```text
当前方式
  已保存的 TOML profile → 兼容核心 → Git / gh 环境 → 现有工具

拟议的原生支持
  上下文选择器 → 共用 DEVWHO_* 变量 → 应用自己的账号映射
```

| 当前适配器 | 兼容核心提供的内容 |
|---|---|
| Git 提交身份和签名 | `GIT_CONFIG_COUNT`、`GIT_CONFIG_KEY_*`、`GIT_CONFIG_VALUE_*` |
| Git SSH 密钥选择 | `GIT_SSH_COMMAND` |
| GitHub CLI 上下文 | `GH_CONFIG_DIR`、`GH_HOST`；`doctor` 可验证实际登录账号 |
| 其他现有应用 | 按字面值配置的环境变量和取消设置项 |

这些应用专属变量是兼容层的输出，不是拟议共用约定的一部分。兼容核心会保留代理等无关设置，也不会反复改写仓库或全局配置。

原生支持和兼容适配可以在同一个终端中共存。启动器可以提供共用约定，同时保留仍需适配器的应用支持。只有实际使用方支持并有迁移路径后，才能移除适配器；单纯发布规范并不足够。

## 兼容核心有多种实现

Python 3.11+ 仍是一种选择。Go、Rust、Bash 独立 core 现在也实现了相同兼容契约，用户可按设备选择一种。Go/Rust 可执行文件运行时不需要 Python 或编译器；Bash 需要 Bash 3.2+、jq 1.6+ 和 Perl 5.18+。源码构建、CI 产物、校验和及当前平台验证情况见[实现指南](../../implementations/README.zh-CN.md)。下载 CI 产物需登录 GitHub；这些是开发构建，尚无正式标签发布。可选的 Go 配置前端提供中英文表单，并写入共用 TOML 配置，不会切换 shell 身份。

[兼容契约](../../spec/compatibility-core-v1.zh-CN.md)与原生环境草案相互独立。各语言移植可以让用户无需 Python 即可使用今天的工具，不必等待应用采用未来的共用约定。

## 现在可以做什么？

- **使用 DevWho：**按照[入门指南](getting-started.md)操作，并从[核心实现](../../implementations/README.zh-CN.md)中选择一种。
- **使用配置表单：**参阅可选的[配置前端](configuration-ui.md)。
- **为应用添加原生支持：**评审这份草案；仓库包含参考使用方示例，但不声称已有第三方采用。
- **为应用添加原生支持：**先与我们讨论这份草案。使用你所选语言的环境变量 API；无需 DevWho SDK。通过应用自己的账号配置解析 profile，并按常规流程验证认证结果。
- **提议新增共用变量：**说明它在多个应用中的共同含义、缺失时的行为，以及它如何避免携带密钥或产生互相冲突的事实来源。
