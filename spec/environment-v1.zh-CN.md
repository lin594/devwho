# DevWho 环境约定——草案修订版 1

[English](environment-v1.md) | [简体中文](environment-v1.zh-CN.md) · [提出缘由](../docs/zh-CN/ecosystem.md)

**状态：提案，不是既有行业标准，也不代表原生应用已采用。** 本文描述上下文提供方与应用之间、与编程语言无关的接口。这里的修订号用于标记本文档版本；它不是环境变量，也不是应用需要协商的值。

讨论：[RFC #1](https://github.com/lin594/devwho/issues/1)。

## 1. 范围与术语

**提供方**会选择一个上下文，并放入进程环境。它可以是 shell 函数、IDE、CI runner、dotenv 加载器或任何 DevWho 实现。它不要求使用特定语言、文件格式、SDK、守护进程或核心安装包。

**使用方**是明确实现此约定的应用。它会把上下文映射到自己的账号或组织配置。本仓库的 Git 和 gh 适配器并不是原生读取这份草案。

**Profile** 是区分大小写的本地上下文标签，不是全局唯一身份、服务用户名、操作系统用户，也不是已认证的证明。同一用户若有多个提供方共用应用映射，必须约定标签含义：在同一映射范围内，`work` 不能代表两个不同的人。重命名标签时，必须更新相关映射。

## 2. 初始完整变量集合

| 变量 | 值 | 含义 |
|---|---|---|
| `DEVWHO_PROFILE` | 非空 ASCII 标签，符合 `[A-Za-z0-9][A-Za-z0-9_.-]*`，区分大小写 | 已选的本地上下文，例如 `personal`、`work` 或 `client-a`。 |

使用规范的大写拼写。没有别名、shell 展开、列表或插值规则。标签是字面数据；使用方不得把它解释为路径名、命令、URL 或创建账号的请求。

支持该约定的原生应用可以通过普通环境获得该值：

```sh
export DEVWHO_PROFILE=work
```

现有 Python 核心已经会在激活时导出此标记。原生使用方可以直接读取，无需再加另一个标记。手动导出该变量不会调用当前 Git/gh 适配器；本仓库也不声称这些工具已经读取它。

| 其他候选项 | 决定 |
|---|---|
| `DEVWHO_SPEC_VERSION` | 不需要：对于稳定且不透明的单一选择器，文档修订和文件格式版本应与进程接口分开。 |
| `DEVWHO_CONTEXT` | 与 profile 选择器重复；第二个标识符必须先有明确使用场景。 |
| 通用姓名/邮箱 | 提交作者、显示姓名和已认证账号是不同概念。归属信息应留在相关应用或适配器配置中。 |
| 服务专属用户名 | 留在应用映射或适配器设置中，不要为每个应用另造一组变量。 |
| 令牌、密码、私钥 | 绝不属于本约定。 |
| 共用应用数据/配置目录 | 应用保留自己的配置和凭据存储。 |

## 3. 读取与选择

对于需要账号的操作，原生使用方应遵守以下规则：

1. 操作中的显式账号选择优先，例如命令行选项或用户有意在应用中选择。不得将该账号与另一个 profile 的凭据或元数据混用。
2. 否则读取 `DEVWHO_PROFILE`。缺失或为空表示没有选定共用上下文：保留应用原有行为。这与当前 CLI 显示 `none` 一致。只含空格或其他格式错误的非空标签属于无效选择，不能当作空值。
3. 通过应用自己的映射解析有效的非空标签。映射缺失或标签格式错误时，在依赖身份的操作前必须要求用户明确选择或清楚报告错误。对于未知 profile，绝不能静默选择默认账号。无关的帮助和只读命令不必因此受阻。
4. 使用应用正常的认证流程，并在适当情况下验证实际账号。该标记永远不是认证凭据，也不能作为提升权限的授权。

例如，应用可以配置 `work → existing-account-entry-42`。这只是说明性数据，不规定映射文件格式。不同应用可以将同一标签映射到不同服务和主机，无需另建一组环境变量。

应在应用常规状态界面或诊断信息中显示解析出的账号。回显 profile 并不能验证登录。应用不得要求读取提供方的 TOML 或 dotenv 文件来发现协议版本。

## 4. 继承与恢复

遵循常规进程继承规则。提供方修改自己的环境，或修改其启动进程的环境。已存在的兄弟进程和编辑器窗口不会改变。除非应用提供自己的显式账号切换界面，否则会在启动时读取上下文；本草案不规定 IPC、轮询或全局当前用户。

激活前先完成校验。支持恢复的 shell 提供方要分别记录变量原先缺失、为空和非空的状态，即使使用方把前两种都视为“未选择”。停用时必须逐项恢复原值。新上下文丢弃的适配器输出或未来字段也应恢复或清除，不能留下过时身份信息。只读或不可写变量必须使激活在改动任何受管变量之前失败。

手动导出变量或加载 dotenv 只会提供环境数据；它不会自动提供 baseline 快照、原子切换、启动默认值/快捷方式或适配器检查。

## 5. 适配器与显式覆盖

本约定用于选择上下文；它不会取代应用的显式选项，不会执行用户认证，也不规定在 rebase/cherry-pick 时更改 Git 作者。必须保留原有作者归属和重放行为。

原生支持和适配器共存时，应用必须说明自身环境覆盖项的优先级。冲突的令牌或账号专属设置必须被诊断，或通过明确的账号选择解决，不得静默混用上下文。当前核心的具体规则见[兼容契约](compatibility-core-v1.zh-CN.md)。

## 6. 无需强制版本变量的演进方式

保持 `DEVWHO_PROFILE` 为不透明的本地选择器。以后不得把它重新解释成 JSON、路径、服务用户名或序列化凭据。狭窄且稳定的含义使不带版本变量的接口成为合理选择。

新增可选能力时，需要记录变量名称、值的格式、缺失时的行为、冲突规则和使用方测试。只有在不影响必要身份或安全行为时，才能忽略未知的可选变量。提供方不能仅因自己设置了某个变量，就假设使用方支持它。

确实不兼容或必需的能力需要单独评审，并明确检测支持情况。不要改造选择器，也不要用本地文件版本掩盖进程接口的破坏性变化。本草案不预先分配推测性的能力标记。

| 版本范围 | 所属位置 |
|---|---|
| 环境约定文档 | 规范修订号和变更记录。 |
| 当前 TOML profile 架构 | 现有 `version = 1`，仅由相应核心/解析器解释。 |
| 内部恢复传输 | 兼容核心使用的私有状态版本。 |
| 未来 dotenv 输入 | 解析器契约；普通键值输入不一定要导出版本变量。 |

Docker Compose 顶层 `version` 已废弃，不再用于选择校验架构。单独一个版本字段并不能定义兼容性。DevWho 保留现有 TOML 版本，是因为解析器确实会校验它；要移除该要求，需要单独制定迁移方案。[Docker 文档](https://docs.docker.com/reference/compose-file/version-and-name/)

## 7. 信任与隐私

将环境输入视为不可信的选择元数据。按数据解析；绝不求值、source，也不根据标签自动打开文件或加载代码。提权进程和服务应遵循自己的环境信任策略，不能信任客户端提供的标记。

标签会继承到子进程，也可能出现在诊断信息中；不要把密钥或敏感个人信息放在标签里。此约定不会隔离共用操作系统账号。使用方仍须执行自己的访问控制。

## 8. 不属于本约定的变量

| 名称 | 当前用途 |
|---|---|
| `DEVWHO_CONFIG` | 选择兼容 CLI 使用的 TOML 文件。原生应用不应依赖它。 |
| `__DEVWHO_STATE` | 未导出的内部 shell 恢复状态，不是应用集成 API。 |
| `GIT_CONFIG_*`、`GIT_SSH_COMMAND`、`GH_CONFIG_DIR`、`GH_HOST` | 由相应工具定义的适配器输出。 |
| `HTTP_PROXY`、`http_proxy` 和其他无关变量 | 除非显式配置，否则切换时会保留。 |

当前核心将 `DEVWHO_*` 保留为通用 profile 环境设置的内部名称，并自行提供 profile 标记。本草案不会改变已安装程序或其文件加载器。dotenv 是单独的[配置格式提案](../docs/zh-CN/configuration-formats.md)。

## 9. 评审与采用条件

- 就稳定的选择器含义、语法、缺失/错误行为、显式账号优先级和未知映射处理达成一致。
- 增加与语言无关的使用方案例，包括当前核心提供的环境和普通 dotenv 加载器提供的环境。
- 验证一个真实使用方：它不导入 Python 核心，也不读取核心私有状态/配置文件。
- 根据真实集成公布采用状态；适配器支持不等于原生采用。
- 根据实际使用方需求评估扩展，并配套测试和兼容理由。

完整核心移植和提供方文件格式的演进都可以独立于原生应用采用继续进行。
